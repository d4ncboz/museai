# muse-video

Every video generated through museai follows this skill. Paths below are relative to this skill folder (`.claude/skills/muse-video/`).

**Always use the skill from `origin/main`**: `git fetch` first, then read this file and run every script from a detached worktree of `origin/main` (`git worktree add --detach ~/Work/museai-main origin/main`, or `git -C ~/Work/museai-main checkout --detach origin/main` to refresh it), never from whatever branch the main checkout happens to be on. EP38 was first built from a checkout 30 commits behind: tone-coloured pinyin (`burn_subs.py`) and dialogue vocab cards (`cards.py`) were missing, and the user noticed. EP41 repeated it from a checkout 56 commits behind (that checkout did not even have this line), so the rule now lives outside the repo: the user-level hook `~/.claude/hooks/museai-skill-fresh.sh` keeps `~/Work/museai-main` on origin/main and denies loading a museai skill, or running its scripts, from a checkout whose skill files differ from main. Developing a skill on a branch: put `MUSE_SKILL_DEV=1` in the command.

Nothing is delivered until `scripts/qa.py` says PASS and the contact sheet looks right (or the user accepts a named failure):
1. **Looks real** - photoreal people and place, no AI artifacts (morphing, extra fingers, warped objects, garbled text).
2. **Fluid motion + continuity** - consistent anatomy, faces, clothes, lighting, object positions. No jitter, stutter, frozen or duplicated frames, flicker, sudden pose changes, sliding. One continuous take by default.
3. **Natural conversation** - attentive listeners, replies at the right moment with brief pauses, no overlap, no awkward delays. Only the speaker's mouth moves.
4. **Lip sync + sound** - every syllable matches lips and jaw, no drift; spoken words = script; clean dialogue, no clipping, music quiet.
5. **One steady pace** - normal everyday speed for the whole video; never rushed, stretched or slowed to fit the clip.
6. **Readable captions** - large, bold, high contrast, outlined, synced, short phrases, never covering faces, mouths, gestures or key objects.

## Style block (automatic)
`scripts/muse-video` appends one style block to every prompt (set `QUALITY=0` only to debug). Edit these files to change the rules for all future videos; don't paste the rules into each prompt.
- `prompt/quality.txt` (default) - people talking: motion / continuity / conversation / lip-sync / speech pace / acting / caption-safe composition / final check. The model renders no text; captions are burned in afterwards.
- `prompt/travel.txt` (`STYLE=travel`) - travel documentary: real geography and landmarks, natural grade and light, slow plausible camera, instrumental music + ambience, no narration, no text on screen.

## Server
- museai FastAPI on 127.0.0.1:18610 (`uv run python -m museai` in the repo root, in a visible terminal tab). Check: `lsof -nP -iTCP:18610 -sTCP:LISTEN`; not listening → start it, wait for "Application startup complete".
- Every job failing within seconds with `cdp_connection_closed` (EP09 v7: twice in a row, no render) means the server's Chrome is gone: restart the server (stop it, `uv run python -m museai`, wait for "browser driver ready") and resubmit. A failed submit is not a take.
- Never print `data/api_key` or `data/accounts.json` (live muse.ai session cookies).
- A job failing with `internal_error` (server log: `TimeoutError` in the browser driver's `_attach`) or `cdp_connection_closed` is a failed submit, not a take (EP27: 3 in a row while the server restarted). Resubmit in a loop: `for i in 1 2 3 4 5; do ... muse-video ...; [ -f ~/Movies/museai/$OUT_NAME ] && break; sleep 60; done`.
- `MUSE2API_VIDEO_TIMEOUT=1500` in `.env` (30-40 s videos take >10 min); a clip of known length gets 360 + 60·duration s (6 s clip → 12 min), then fails over to another account.
- No video job renders longer than 30 min in all (`MUSE2API_VIDEO_JOB_DEADLINE=1800`, failovers included); then it fails with `upstream_timeout`. An account whose render timed out gets no new video job for 30 min while another account is usable (`MUSE2API_STUCK_VIDEO_COOLDOWN=1800`), so new clips go to a ready account instead of queueing behind a stuck tab (EP48-50: one account timed out five clips in a row, 12 min each). Don't wait on a job past 30 min or babysit a slow one: on `upstream_timeout`, resubmit once (it lands on a ready account); a second timeout is a real failure, report it. Never restart the server to unstick one render.
- Results also land in `data/media/vid_*.mp4`; copy each raw render into the working folder right away.
- Each account renders one video at a time; with N enabled accounts, N videos render in parallel. Extra requests queue for the next free account (`MUSE2API_MEDIA_QUEUE_TIMEOUT`, default 0 = no limit), so independent videos can be submitted at once. Sending the same prompt (and first frame) again while it is still queued or running returns the same task, not a second render: submit each clip once and wait for it. A free account never sits idle while a request waits: one agent session may render on every free account at once. `scripts/muse-video` sends `X-Muse-Session` (default `$CLAUDE_CODE_SESSION_ID`); when accounts run short, the next free one goes to the waiting session holding the fewest renders, so no session starves the others. So submit independent clips at once, each in its own background `muse-video` call: separate shots of a travel video, separate episodes, a clip and an unrelated one. Clips of one multi-clip video still render in order (each needs the previous last frame).
- Add an account: export cookies from a logged-in https://muse.ai tab (Cookie-Editor JSON), then `uv run python scripts/import_account.py <export.json> --label muse-N` in the repo root (keeps only session cookies, checks the session). Delete the export afterwards. Every account is premium; never take one out of video jobs because of a bad render without proof.

## Before rendering: fit the script to the clip
`python3 scripts/budget.py script.txt <duration>` (a file with the dialogue lines only; run on the full prompt it counts every line and overshoots) - needs ≤ duration and ≥ 75 % of it at 4.5 syllables/s. TOO LONG → shorten the script (keep the meaning) or extend the clip. TOO SHORT → add a natural line or shorten the clip (an under-filled clip gets padded with silent pauses). The total video length is not a target: it follows the dialogue at a natural pace. Never ask the model to speed up or slow down instead. Split lines over 14 syllables.

## Generate one clip
```
SIZE=9:16 DURATION=40 OUT_NAME=clip.mp4 NO_OPEN=1 scripts/muse-video -f prompt.txt
```
Output in `~/Movies/museai/`. The video length comes from the prompt: always set `DURATION`, and the script adds an OUTPUT line asking for exactly that many seconds in full HD 1080p (1080x1920 for 9:16); `STYLE=travel` asks for 4K UHD first, falling back to 1080p. It prints the delivered length and size and never rejects or blocks a render. `IMAGE=first.png` sets the first frame. A busy account (`no_account_available`), a server restart (`interrupted`) or a down server are retried automatically (`RETRIES=15`, `RETRY_WAIT=120` s), so one call yields one finished video; run it in the background and don't resubmit by hand. If muse replies with text only (`upstream_refused`), prepend "NEW STANDALONE REQUEST. Ignore any earlier versions, drafts or projects. Generate one new video from scratch and return the finished video file in this reply. Do not reply with text only." and retry. Start every re-render that passes a new `IMAGE=` with "NEW STANDALONE REQUEST. Ignore any earlier versions, drafts, images or projects. Use ONLY the image attached to this message as the first frame.": EP20 clip A take 2 got a new still but muse rendered from the previous take's still in the same thread.

## Prompt (per video; the quality block is added for you)
EVERYDAY CHINESE briefs: the user's format, the episode log and the rules for drafting the next episode are in `prompt/everyday-chinese.md`; add each new episode to its log. Follow its "Viral rules": the hook in the first 1-2 s is the everyday problem, never a greeting; the ending is a quiz that echoes the hook; the title and cover name the dilemma.
Sections: CAST, SETTING, VOICE, CAMERA, SCRIPT.
- **Recurring travel character**: a travel video with a person on screen uses the AI character of `../zoominview/SKILL.md` "The character" (`IMAGE=` her face photo + her fixed description), never a real person's photo.
- **CAST**: age, ethnicity, hair, exact outfit colours, voice type per person. "Keep faces, hairstyles, outfits, props and voices identical for the whole video."
- **SETTING**: one real, specific place with a few concrete objects that stay where they are.
- **VOICE**: language + accent, e.g. "Natural Standard Mandarin (Putonghua), accurate tones, warm everyday intonation, about 4.5 syllables per second for every line." Optional "very quiet instrumental music far below the dialogue", or none.
- **EYE LINE** (every dialogue video): add to CAMERA "Eye line: while talking and while listening, each person's eyes rest on the other person's face. Eyes never wander to the room, the counter, the floor or the lens, never stare past the other person, never half-close. Heads turn only partway toward each other; the eyes carry the rest of the look." EP12 had only "look at each other": muse put the woman in side profile with her eyes drifting past the man on every dialogue line, and the man half-turned to the lens in the ending; the user saw it as AI generated. `gaze.py` (in `check_clip.sh` with `GAZE=`, and qa.py's `gaze` check with `GAZE=` one letter per cue: W/M speaker, C to camera) measures head yaw + iris per face; side profile counts as off because the eyes cannot be read.
- **CAMERA**: default "One continuous take, steady locked camera, medium two-shot framed from the waist up, both bodies face the camera squarely, each person turns only the head partway toward the other (front three-quarter view, both eyes and the whole mouth visible, never side profile), faces large in the upper half of the frame." ## Short renders
muse has returned 10 s 720x1280 clips for 30 s requests (2026-10-26), on muse pro accounts, while replying "Generating your 30-second video". The OUTPUT line states the length and 1080p explicitly to steer it. If a clip still comes back short, tell the user the length and size the script printed; don't disable accounts for it. A first render that comes back 10 s with the whole script squeezed into it is unusable (rushed speech): switch to a multi-clip plan right away instead of retrying the single render (EP06: 30 s request -> 10 s clip with 8 of 12 lines).

## Multi-clip videos (continuity) - ALWAYS
The last frame of clip N-1 is the first frame of clip N.
1. **Plan in 10 s clips.** Split the script so each clip holds 7-8 s of speech (30-36 syllables, about 4 short lines, `budget.py part.txt 8` must say OK, not TOO SHORT), and each clip's prompt says `PART n of N`, 10 seconds, its own lines only. Put an intro cut in clip 1 and a turn to camera in the last clip. Render with `DURATION=10`. An under-filled clip gets padded with silence whatever the TIMING text says (EP09 clip 3: 21 syllables in 10 s -> 1 s lead-in + 2.3 s pause in every take; clip 1 with 3 lines had a 3.5 s silent tail). Move lines between clips until every clip is full, the last clip included.
   **Submit each clip once** (one request, one account). If it fails its check, re-render it once, one request at a time; never render parallel takes of the same clip. Independent clips (no shared first frame) go out at once; the server spreads them over the free accounts. The server also never renders the same request twice: an identical request still running joins it, and one that finished in the last hour returns that clip. To re-render a clip that failed its check, run it with `RETAKE=1`.
2. Render clip 1 normally; render every next clip with `CONTINUE_FROM=<previous clip>` (grabs its last frame as the first frame and prepends a CONTINUITY instruction). Never put a title or label line in a clip prompt (no "EVERYDAY CHINESE #NN — …", no "ENDING PART."); start it with "NO TEXT ON SCREEN" instead. EP38: muse drew the prompt's first line, "EVERYDAY CHINESE #38 — … ENDING PART.", as on-screen text in a CONTINUE_FROM clip; it was covered in post with a feathered patch of the static wall taken from an earlier frame.
3. Same cast, outfits, setting, lighting, camera position, action and gaze as the previous clip's ending. End each clip on a calm resting pose.
4. **Check every clip before chaining**: `scripts/check_clip.sh clip.mp4 [previous.mp4]` (cuts, transcript, sheet with the seam), then `pron.py` on the clip with its own cues (below). Re-render the clip, before rendering the next one, if it has a cut you did not ask for, a person outside the cast (EP06: a shopper walked in behind them in the last 0.8 s, together with a second cut), words not in the script (EP06: the assistant answered the ending question with 合身的), the listener turning to the camera with the speaker, or any `jumps:` line (a one-frame snap of pose/face inside the clip; EP09 v7 clip B snapped 6 times and the user saw the glitches; aligning the frames left a diff of 7-10, so no post fix hides it). Add `SCRIPT=script.txt` ("W: line" per line) so it also runs the speakers check on the clip: `WRONG VOICE` means re-render; `LISTENER MOUTH MOVES` does not need a re-render (the reframe step fixes those lines in post). Add `GAZE=O` on a dialogue-only clip (`C` on a to-camera clip) so it runs `gaze.py`: `OFF GAZE` (a face in side profile, eyes on the room, floor or lens instead of the other person) means re-render; no edit fixes an eye line. Everything after a bad clip has to be re-rendered, so catch it here.
5. **Trim silence at the seams** (cutting the ends of a clip does not retime anything, so lip sync is kept): cut each clip about 0.4 s after its last syllable *before* using it as `CONTINUE_FROM` (EP06 clip 1 had 2 s of music-only tail), and cut a continued clip's silent lead-in (EP06 clip 3 started speaking at 2.5 s). The lead-in often drifts or zooms slightly, so cut as little as needed and check the seam again. `ffmpeg -t <end> -c:v libx264 -crf 16 ...` / `ffmpeg -ss <start> ...`.
6. **Fix cuts and pauses in post when re-renders keep failing** (`scripts/cutedit.py plan.json out.mp4`, segments of the clips joined with hard cuts; nothing is retimed):
   - Intro cut missing (EP09: 3 of 4 clip-1 takes stayed in the two-shot, man half in the intro): cut from the intro clip to the two-shot clip *inside the pause after the intro line*, which also drops that pause. Never punch in (crop) on one face: the user wants one steady medium two-shot, no close-ups, zooms or punch-ins (EP10 v3 used punch-ins on a miming listener and was rejected).
   - Listener turns to camera at the ending, or a long pause before the last line: re-render that clip, or cut inside the pause to the same two-shot framing from another take.
   - Pauses inside one continuous take cannot be cut without a jump: re-render that clip or name the failure.
   - Find cut points with `python3 scripts/gaps.py video.mp4` (energy-based speech spans and gaps).
   - Trimmed pauses shorten the video: if it falls under 30 s, add a natural line (needs the user's OK when the brief fixes the script) rather than leaving pauses in.
7. Join with `scripts/stitch.sh out.mp4 part1.mp4 part2.mp4 ...`: denoises each clip (`afftdn`; EP10 clips 2-4 came back with a white hiss floor at -51 dB above 7 kHz, which loudness matching raised to an audible -46 dB; the clean clip sat at -86 dB), drops the duplicate first frame and cuts each clip's audio to its kept frames (EP10: trimmed clips carry up to 25 ms more audio than video, and the dropped frame's audio stayed in; both pushed later clips' voices off their lips and left the join at 23.8 fps), scales every clip to the first one's size (muse returned clip 2 of a 1080p chain at 720x1280), and evens out loudness between clips (EP06 clips came back 8 dB apart). **Ease the seams first, always**: continued clips start reframed (EP09 v7: 3.7-4.2 % zoom and ~10 px shift at both seams, YDIF 17 vs ~0.6 per frame; the user saw it as an AI glitch). `uv run --no-project --python 3.12 --with opencv-python-headless==4.10.0.84 python scripts/ease_seams.py eased part1.mp4 part2.mp4 ...` measures each seam and spreads the reframe over 1.5 s (`EASE`) as a slow camera move on the tighter side, nothing retimed, so it works over speech (EP09: frame diff 20 → 2-3 at both seams). Scale every clip to one size first (`scale=1080:1920:flags=lanczos`): mixed 720p/1080p clips make `findTransformECC` fail to converge at the seam (EP31). Stitch the eased clips: `scripts/stitch.sh out.mp4 eased/part1.mp4 eased/part2.mp4 ...`; `python3 scripts/jumps.py out.mp4` must say `RESULT ok` (qa's smooth check fails on any jump left). `XFADE=0.25` in stitch.sh is only for a seam that is a real change of shot, never over speech. A seam that ease_seams.py reports as `RESIDUAL` (pose changed, not just framing; EP44 A→B left 4.7) gets a short dissolve on its silent join only: `XFADE=0.12 XFADE_AT=<seam no.> stitch.sh ...`; the other seams stay hard joins. Then shorten long pauses: `python3 scripts/shorten_pauses.py stitched.mp4 tight.mp4` (it joins with a 0.2 s xfade, so a pause at a planned hard cut becomes a dissolve: EP23 lost its intro cut this way. Trim the intro and the next clip at that seam by hand before stitching instead) cuts every pause > 1.0 s down to ~0.45-0.6 s inside the silence with a 0.2 s dissolve, placed on the most alike frame pair in the pause and printing that pair's diff (four muse dialogue pauses: 3.8 → 1.2, 5.3 → 3.2, 4.0 → 2.1 against a mid-pause cut). `SHIFT` on a pause means she moves through all of it and the dissolve would read as the view jumping (user, EP44): `KEEP=` that pause or cut it by hand on a still stretch. jumps.py does not see dissolves, so read those lines (EP08: five 1-2 s pauses, 27.9 → 22.3 s, no syllable moved). Loud muse music hides the pauses from it: run demucs on the stitched audio and pass the vocal stem as `SPANS_FROM=voc.mp4` (EP29). Subtitle and QA the result. Its dissolve must land on still frames: across a head turn it shows a ghost double face (EP36, the pause before the recap turn). Then `KEEP=` that pause and cut it by hand with a 0.25 s xfade on the still stretch before the turn (pick the frame pair with the lowest diff), and check `jumps.py` again.
8. **Dub the stitched file (every multi-clip dialogue video; qa.py's `voices` check fails without it)**: EP09 v7 skipped this step, passed every other check, and the user heard both characters' voices change between lines (voices.py: same-speaker similarity 0.51-0.68 raw, 0.74-0.84 dubbed). each muse render picks its own voices, so a person's voice, timbre and accent change at every seam (EP08: the woman 183-258 Hz across 4 clips, the clerk a different man each clip). Prompting the same voice does not hold it. Build cues.json first (step 2 below), then `uv run --no-project --python 3.12 --with edge-tts --with librosa --with soundfile python scripts/dub.py stitched.mp4 cues.json WMWM... dubbed.mp4`: one fixed voice per person, cloned (F5-TTS, `clone_tts.py`) from the voice bank `voices/`: natural muse voices cut from earlier renders, least recently used first so episodes don't all sound alike, kept per output path so a re-dub keeps them (`voicebank.py list` shows them and when each was last used). The fixed edge-tts pair (Xiaoxiao + Yunjian) on every episode sounded like AI and like the same two people every day (user, 2026-10-29). `VOICE_W` / `VOICE_M` take a bank id (`W-mid-01`), a glob (`M-low-*` for a deep-voiced clerk) or an edge-tts name (`zh-CN-XiaoxiaoNeural`) as the fallback when a cloned line fails pron.py. Grow the bank after new renders: `voicebank.py harvest data/media/vid_*.mp4` (command in its docstring) keeps only lines Whisper hears as the SCRIPT says them, text and audio cut to the same words: a reference whose text the audio does not say (muse slurred 包裹, a cut-off 十五) made the clone add a sound before every line (EP42 付好了 -> Save好了, 请问 -> 给请问). `clone_tts.py` hears every cloned line back (Whisper) and retakes a misheard one; `CLONE MISHEARD` in dub.py's output names a line no take got right: dub that video with an edge-tts voice for that person, each line starting on the original lips (split at commas where the original pauses) and playing at the voice's own speed, running on into the following silence when the lips were faster. Never time-stretch or push the voice past +20 % (EP08: +40 % plus a phase-vocoder stretch sounded pitched and unnatural to the user). It prints each part's voice length vs the lip span; `OVERRUN` means it runs into the next part or speaker. It also writes `dubbed.cues.json`, the cues retimed to the new voice: burn captions and run qa.py / speakers.py with that file, not the lip-timed cues (those end with the lips, so captions vanish early and qa reads a normal-speed voice as too fast). The voice is never pitch-shifted, slowed or time-stretched, and `MAX_PCT` cannot go above 20. ## Fixing a delivered video
When the user reports a problem (wrong word, miming listener, bad seam, caption, sound), fix only the broken part and rebuild; never re-render the whole video for a local problem.
1. **Update the skill first** (see "Maintaining this skill"): add the rule, prompt wording or check (prefer a `qa.py` / `check_clip.sh` gate over a sentence) that would have caught it, so the next video does not repeat it.
2. **Get the parts back**: before the final delivery the work folder is still in place; after it, restore it from `~/.Trash` (the final deliver.sh put it there; the agent may lack Trash access, so ask the user to put it back). Find the broken span: which clip, which line, which seconds.
3. **Fix the smallest unit**, cheapest first:
   - post only, no render: captions (rerun `burn_subs.py` with fixed `cues.json`), pauses (`shorten_pauses.py`), a cut or reframe (`cutedit.py`), loudness or seams (`stitch.sh`, `ease_seams.py`);
   - one line wrong: move or cut it at a clip boundary (see pronunciation above) before re-rendering anything;
   - one clip unusable: re-render only that clip with `CONTINUE_FROM` the clip before it. Keep the clips after it: trim the new clip's tail to a resting pose and smooth the join to the next clip with `ease_seams.py`; re-render a later clip only if `jumps.py` still fails at that seam.
4. **Rebuild**: `stitch.sh` with the kept + fixed clips, burn captions, run `qa.py` and the frame check, then the preview again (`FINAL=1 deliver.sh` only once the user accepts) and clean up after the final one. Tell the user which part changed.

**Shared steps for place videos** (scenic-drop-reel, zoominview, scenery-director, travel; each skill names only where it differs):
1. **Earlier shots**: `python3 ../shot-history/scripts/shots.py check --place "<place>" --country <country>`. `ALREADY SHOT` → follow `../shot-history/SKILL.md` (new views, ask the user before rendering).
2. **Brief the real place**: name the real landmarks, terrain, water and vegetation. muse paints green forests and meadows on any mountain or fjord (Svalbard reel, 2026-10-28: pine forest on the peaks and around the Seed Vault); for treeless places (Arctic, Iceland highlands, deserts) write into every brief "NO trees, NO forest, NO bushes, NO green meadows anywhere; only bare rock, scree, snow, ice and brownish tundra".
3. **Render** independent clips at once, each in its own background call (see Server); clips that continue each other render in order.
4. **Music** in parallel with the renders, from the shared engine (`scripts/music.py`, see "Music" below).
5. **Check each clip**: `python3 scripts/qa.py clip.mp4 --travel 0 sheet.jpg`; judge `smooth` and the sheet (planned pans and zooms trip `motion` TIME-LAPSE: check frames instead). A clip with no audio track reports `sound`/`noise` as `skip no audio stream` (the reel's music replaces it).
6. **Compose** with the format's `compose.py`, then the same qa run on the result and a contact sheet (`ffmpeg -i <final> -vf "fps=2,scale=180:-1,tile=8x4" -frames:v 1 sheet.png`).
7. **Deliver** with `scripts/deliver.sh`: preview first, `FINAL=1` after the user accepts, thumbnails (`../thumbnail/SKILL.md`, `THUMB_DIR=`) and per-platform captions (`../social-captions/SKILL.md`, `CAPTIONS_FILE=`; the first line is a scroll-stopping hook, never the reel length or a format label). Record the delivered shots with `../shot-history/scripts/shots.py record` **before** `FINAL=1`: it trashes the work folder.

## Music (shared engine)
`scripts/music.py` makes the track for every format (scenic-drop-reel from its plan, zoominview through `scripts/music`, product-ad with `--style`); `scripts/ace_song.py` runs inside the ACE-Step venv for it. It writes `track.m4a` plus `track.beats.json` (beat grid, drop) that each `compose.py` cuts on.
- **ace** (default when installed): ACE-Step sings the lyrics (Apache-2.0, ok for commercial posts). Install once (~8 GB, needs the user's OK):
  ```bash
  git clone --depth 1 https://github.com/ace-step/ACE-Step ~/.local/share/ace-step/repo
  uv venv --python 3.11 ~/.local/share/ace-step/venv
  uv pip install --python ~/.local/share/ace-step/venv/bin/python -e ~/.local/share/ace-step/repo
  ```
  Weights (~7.7 GB) download on first use - set `HF_HUB_DISABLE_XET=1` if the big files sit at 0 B (2026-10-28: Xet hung, plain HTTP took 6 min). A 40 s song renders in ~2 min on an M1 Pro (model load 23 s).
- **ACE ignores the BPM tag** (asked 88, got 79; asked 100, played 131; asked 72, sang 92). music.py never time-stretches an ACE song: the phase-vocoder stretch (Kirkjufell reel, 134→108 BPM) made the singer sound pitched and robotic. The song keeps its own tempo (half/double-time nearest the asked BPM) and the beat file follows it, so plan in seconds and let compose snap to the real beats. ACE often misses the tempo by 20-30 %, so `music.py` re-renders on the next seed (up to 3 renders) until the song is within 10 % of the asked BPM, and keeps the closest one. MusicGen (instrumental) is still stretched to the BPM.
- **Singer sounds human**: one natural lead singer in a low warm register, in balance with the band (no duets). `generate_ace` drops negated phrases ("no autotune" pulled the voice robotic and pitched again on the Zhangjiajie reel, 2026-10-31), 100 steps at guidance 10 (15 gave a strained voice), loudnorm to -14 LUFS without a tanh drive (it made the voice harsh).
- **Real voice, never a pitched robot** (user rule 2026-11-02, Fuji reel: "hushed male vocal" sang at a median 259 Hz, snapped to the semitone like autotune): `generate_ace` asks for a baritone male (alto female) chest voice in speaking range with natural vibrato and pitch drift, and drops hushed/airy/whispered/breathy/falsetto from the tags. `voice_check` splits the lead vocal (demucs) and fails a take whose median pitch is above 180 Hz (male) / 300 Hz (female) or that sits under 14 cents off the nearest semitone; `music.py` then tries the next seed (4 takes), keeping a natural voice before the closest tempo. All 4 takes hold the machine-wide ACE lock together (released between takes, other sessions took it and each take waited 15-40 min). `warning: no take had a natural voice` → never deliver it unheard; offer an instrumental track instead: copy the plan with `lyrics` emptied and instrument-only tags (e.g. "traditional Japanese instrumental, koto melody, shamisen accents, shakuhachi flute, soft taiko, no vocals") and run `music.py --engine musicgen`, no ACE queue, ~2 min. Fuji reel 2026-11-02: all 4 ACE takes sang at 198-311 Hz and 3 of 4 under 11 cents whatever the voice wording; the user picked the instrumental koto track.
- One ACE render per machine: `music.py` holds `~/.local/share/ace-step/render.lock` while ACE runs, so a second video (another session) waits instead of sharing the GPU (two at once: model load 40 → 285 s, 100+ s per step). Never `pkill` ACE: the process may belong to another session.
- **musicgen** (fallback, instrumental): MusicGen medium, ~10 min per track on Apple silicon, first run ~8 GB. Weights CC-BY-NC 4.0: personal posts only - say so when the user wants to monetise.
- `--raw x.raw.wav` re-shapes a saved render; `--seed` for another take. Check the spectrogram (`ffmpeg -i t.m4a -lavfi showspectrumpic=s=1200x300 s.png`) and listen to the cut before composing: only the ear can tell the hook is in it.
- A reference reel's own audio stays out of the repo (audio is gitignored); a user-supplied track goes in with `--music file --bpm N --drop T` (scenic-drop-reel) or a file style (zoominview).

## Travel videos (`STYLE=travel`)
Real destination, no dialogue, no captions. Brief, file name (`travel-<slug>`), shot history and delivery follow "Format skills" above. Rules 3-6 above don't apply; rules 1-2 do.
**Default for every travel / place request (user rule, 2026-10-28): the drone reel in `../scenic-drop-reel/SKILL.md`** (aerial drone shots cut on the beat, random template), also when the request only names a place or attaches a photo of it ("generate for Svalbard"). Use the single-shot documentary below only when the user asks for one continuous shot, a calm/locked view or "documentary mode"; a "cinematic scenery" / "director" / series-episode request, or one for a ready-to-paste video prompt, goes to `../scenery-director/SKILL.md`.
1. **Prompt** sections: PLACE, TIME + WEATHER, SHOTS, MUSIC.
   - **PLACE**: real named location + the concrete landmarks/terrain actually there (e.g. "Ha Long Bay, Vietnam: limestone karsts rising from emerald water, wooden junk boats"). Never ask for things that are not there.
   - **TIME + WEATHER**: one time of day and weather for the whole clip (e.g. "early morning, light mist, soft low sun from the left").
   - **SHOTS**: default one continuous shot with one slow move (drone push-in, slow pan, gentle dolly). Multiple shots only if asked; list them in order with the move per shot.
   - **Rules carried over from the drone reels (user, 2026-10-28)**: open on the most striking view, since the first 2 s decide whether viewers stay; keep shorts 10-18 s and end on a frame that flows back into the first so the replay loops; keep every move slow and level so nobody gets dizzy; name the real vegetation in PLACE (muse painted pine forest on Svalbard until the brief said "NO trees, NO forest, NO green meadows; only bare rock, scree, snow, ice and brownish tundra"); music in MUSIC fits the scenery (icy folk for the Arctic, ukulele for a beach), never one genre for every place.
   - **MUSIC**: instrument + mood matching the place (e.g. "soft đàn bầu and strings, calm"), plus the ambience (waves, birds, wind).
2. **Render**: `STYLE=travel SIZE=16:9 DURATION=10 OUT_NAME=place.mp4 NO_OPEN=1 scripts/muse-video -f prompt.txt` (`SIZE=9:16` for shorts). Longer → multi-clip with `CONTINUE_FROM`, same as above.
   - **Asked for more than 10 s, muse may join its own clips**: a 15 s Lauterbrunnen request (2026-10-26) came back 15 s 1080x1920, but at 10.04 s it cut back to ground level with different light (qa: `cuts at [10.04]`). Keep the good part up to the cut (`ffmpeg -t <cut>`) and render the rest as a `CONTINUE_FROM` clip instead of re-rendering the whole video.
     The join can also be a dissolve that qa does not see: a 15 s Positano image-to-video (2026-10-27, `IMAGE=` first frame) dissolved at 5.75-6.5 s into another view (tiled dome turned plain grey, calm blue sea turned turquoise with whitecaps, framing lower) and qa said `cuts at []`, PASS. Look for this on the contact sheet of every render over 10 s; keep the part before the dissolve and continue from it the same way.
   - **A continued clip pans away unless the camera is locked**: Positano part 2 with "almost imperceptible sideways drift, slowing, then still" panned right and down from ~4 s until the dome left the frame. The re-render with "LOCKED-OFF CAMERA ON A HEAVY TRIPOD FOR ALL 10 SECONDS ... does not pan, tilt, slide, drift, push in, pull out or zoom ... every building stays at exactly the same pixel position and size ... only nature moves" held the frame for all 10 s. Use the locked wording for every continued travel clip, written as "THE CAMERA IS COMPLETELY LOCKED OFF" without the tripod (muse drew one into Skógafoss, see Waterfalls below); any drift the brief wants already happens in the first clip.
     An image-to-video first clip drifts away too: Cala Goloritzé 15 s from a photo (2026-10-27) asked for "extremely slow lateral drift to the right, about 3 % of the frame width, constant focal length, never zooms" and panned right from ~5 s until the pinnacle left the frame and invented red cliffs came in (qa: `TIME-LAPSE` on the lower bands only). The re-render with the locked wording plus "the framing of the last frame is identical to the first frame ... nothing new comes into view at any edge" held for all 15 s and passed. With `IMAGE=`, use the locked wording from the first render and drop the drift the brief asks for; tell the user.
   - **Two renders bring two music takes**: `stitch.sh` joins audio hard, so the music jumps at the seam. When the first clip was cut out of a longer render, crossfade its own audio past the cut into the next clip's audio (0.8 s `afade` out/in + `amix`, then `loudnorm`) and keep the stitched video stream (`-c:v copy`).
   - **Continued clips start reframed**: the first frame of a `CONTINUE_FROM` clip is slightly shifted and zoomed against the given frame, so the join jumps for one frame (frame difference 14 vs ~5 elsewhere, below the hard-cut threshold, so qa still passes). A re-render with "first frame pixel-identical, no reframing" jumped the same. Run `scripts/ease_seams.py` on the clips before `stitch.sh` (multi-clip step 7): it turns the reframe into a 1.5 s slow camera move, keeps every frame, and works for dialogue too (a crossfade over speech would blend two mouths). `jumps.py` on the joined file must say `RESULT ok`.
   - **"No zoom" still gets a push-in**: asked for a near-static lateral glide with "no zooms, no change in shot size, 2-3 m travel", a 15 s Lake Bled render (2026-10-26) pushed in over the first ~7 s (island ~2x bigger, foreground reeds left the frame), then held; qa passes this, so judge shot size on the contact sheet. Adding "slider at water level, constant focal length, never moves forward or backward, never zooms, the island stays exactly the same size in every frame, foreground trees and reeds stay in frame" halved it (island ~1.5x, reeds kept) but did not remove it. Use that wording from the first render, and tell the user about any push-in left.
   - **Image-to-video motion: neither time-lapse nor frozen photo**: Hallstatt 15 s from a photo (2026-10-27, locked camera). Take 1 ran the sky as a time-lapse (clouds filled the sky, `motion.py`: sky drifting 9.7 % of width/s). Take 2 asked for "barely noticeable" motion and "the sky in the last frame looks almost the same as in the first": muse froze everything and only warped the lake in place (sky/mist/village 0.00, lake coherence 0.04-0.07); the user saw the view "shaking like a current" instead of flowing water, and qa still said PASS. Never ask for "barely noticeable" or "same as the first frame". Take 3 asked for real-time ripples plus mist/clouds drifting "about a tenth of the frame width in 15 s": the ripples travelled, but the sky still ran at 3.3 %/s, the mist grew and the light darkened. Take 4 passed (sky 0.6 %/s, lake ripples travelling, coherence 0.12-0.19) with "REAL-TIME FOOTAGE, NOT A TIME-LAPSE. Only the water clearly moves" and the sky described as 15 real seconds: same clouds in the same places, drifting only a few pixels, no new or growing clouds, mist keeps its size and height, light unchanged; the mist still thickened somewhat in the last third, which motion.py does not catch, so check the sheet for it. Never give the sky a drift distance. **Scenes without water** (Bastei Bridge 15 s from a photo, 2026-10-27, locked camera, motion = foliage swaying + sky): take 1 redrew the view at ~2 s (foreground boulders gone, new pines grown, sky and light changed) with no cut, so qa's smooth check passed it; only frame grabs at 0/1/2 s showed it. Take 2 added "the first frame holds for the whole video ... no new trees, the sky keeps the same pale blue": the view held but froze (STILL PHOTO). Take 3 added "live moving footage, not a still photo" + "cloud wisps drift slowly to the right at real speed": sky ran as a time-lapse (4 %/s, clouds building, a sun flare came and went) and the swaying lower gorge read as WOBBLE. Swaying trees alone never gave motion.py a coherent travelling band; a waterless photo has no reliable motion source yet, so grab frames at 0, 1, 2 s of every image-to-video take and tell the user up front that the result may be near-still.
`prompt/travel.txt` NATURE MOTION carries this wording plus real-time travelling ripples and rigid buildings; give the brief's own motion the same concrete terms (direction, how far it moves). `qa.py --travel` runs `motion.py` and fails STILL PHOTO, WOBBLE and TIME-LAPSE.
   - **Sea seen from above: describe wave events, not a flow direction**: Cala Goloritzé 15 s from a photo (2026-10-27). Take 2 ("small waves roll toward the beach ... glints travel across the surface") passed qa, but the user saw unnatural water: the whole sea was one glitter texture sliding slowly down-frame, away from the beach, at constant speed (open-water optical flow dy +0.02 every second, no sets, no breaking foam). Take 3 spelled out direction, swell sets and speeds in five bullets: muse flew the camera forward and down, replaced the sky and cut to another view at 10 s. Take 4 held the camera and the water looked right with three short lines: waves break on the pebbles and the arch at irregular moments and spots (foam runs up, slides back, dissolves); the open surface rises and falls with small ripples and twinkling glints and "does not flow, stream or slide in any direction as one sheet"; seabed rocks stay fixed. Measure open-water flow over time (mean dx/dy per second in the sea band): one constant direction for 15 s is the sliding sheet, whatever `motion.py` says. Take 4 still tilted the camera from 9.6 s to the end. Two `CONTINUE_FROM` takes from its 9.5 s frame both moved too (one tilted for all 10 s; the other tilted for 3 s and settled on a wider, higher view, so the join would show a 20 % zoom-out). What worked: keep the one render, whose water and music already run through, and cancel the late move in post with `scripts/lock_camera.py in.mp4 out.mp4 9.5` (aligns later frames to the 9.5 s frame on the rocks, one fixed 7 % crop for the whole video, nothing retimed): rock motion 48 → < 1.3 px/s, `jumps.py` ok, qa PASS, user accepted the water. Try this before continuing a travel take whose only flaw is a late camera move.
   - **Waterfalls: ask for the fall speed, never name a tripod**: Skógafoss 15 s from a photo (2026-10-27, locked camera). Take 1 with "pours down powerfully at true real-world speed" left the curtain shimmering in place (qa WOBBLE; the falls region still correlated 0.93 with itself after 0.5 s, the river changed more than the falls). Take 2 asked "THE WATERFALL MUST VISIBLY FALL, FAST ... race from the lip to the base in about three seconds ... the white pattern is completely different every half second": the water fell, but "LOCKED-OFF CAMERA ON A HEAVY TRIPOD" made muse draw a tripod with a camera standing in the river, and it ignored the first frame. Take 3 kept the fall wording and said "THE CAMERA IS COMPLETELY LOCKED OFF ... The camera is never seen: no tripod, camera, equipment or person appears anywhere in the picture": matched the photo, frame held (<= 0.6 % scale, 3 px), water fell. Never put a tripod, rig or camera noun in a prompt; zoom into the frame edges and base of every take for invented equipment. qa then fails `motion` with TIME-LAPSE on the falls bands: that is the water falling (optical flow straight down, coherence ~1.0, 5-6 px/frame at 540 px wide), not a time-lapse. Confirm the flagged bands move down only over the water and the cliffs beside them stay at mag ~0.01, then accept it; a TIME-LAPSE band whose flow is sideways or over sky is still a failure.
3. **QA**: `python3 scripts/qa.py video.mp4 --travel [planned_cuts=0] sheet.jpg` - format 1920x1080 or 1080x1920 (or their 4K sizes), 24-30 fps; no clipping, mean > -35 dB; smooth as above; motion (`motion.py`, optical flow per 10 % band): something travels (not STILL PHOTO), no band moving in place with coherence < 0.12 (WOBBLE), no band drifting coherently > 3 % of width/s (TIME-LAPSE). The sheet cannot show any of these: a frozen take and a wobbling take both look fine as stills. Contact sheet (12 even frames): real place, no invented landmarks, warped buildings, repeated mountains, HDR halos, text or watermarks; same light and weather throughout. FAIL → re-render with the failing rule quoted more strongly.
4. No captions, no burn step. After PASS + sheet check, show the preview from the work folder; once the user accepts it, ask whether they want 4K: yes → `UHD=1 FINAL=1 scripts/deliver.sh` (in the background), no → `FINAL=1 scripts/deliver.sh` (1080p). Either way pass `THUMB_DIR=` (thumbnails: `../thumbnail/SKILL.md` style `travel` on the raw shots); the video and its two thumbnails are the only Desktop files.

## Maintaining this skill
Agents update this skill directly, without asking, whenever a render, QA run or user correction teaches something new: fix the rule here, in `prompt/*.txt` or in `scripts/`, then run the whole flow on autopilot, never asking the user:
1. Branch from the latest `origin/main` (`git fetch origin main`), commit, push the branch, `gh pr create`.
2. Before merging, `git fetch origin main` again; if the PR is `CONFLICTING`/`DIRTY`, rebase onto `origin/main`, resolve keeping both sides' rules (main's newer text plus this change), check scripts (`bash -n`, `python3 -m py_compile`), `git push --force-with-lease`.
3. `gh pr merge <n> --squash --delete-branch` once it is `MERGEABLE`, then switch the checkout back to the updated main and delete the local branch.
Name the base branch only through `origin/main` refs or `gh` defaults: a hook blocks any command that looks like a push to main (e.g. `gh pr create --base main` in the same command as `git push`), so run push, PR create and merge as separate commands.
 The skill lives only in this repo; never copy it to `~/.claude/skills/` or another folder. Record only lessons proven by a render, not guesses.
